## Components

### 1. `git sync` — Real Implementation (commands/git.ts)

Current behavior: `console.log("git sync: would commit ...")` for each stage.

Target behavior:
1. Validate we're in a git working tree (`git rev-parse --git-dir` succeeds); else exit 2.
2. Validate `cycleEntry.platform` is set (with sensible fallback to `configFromEnv()` + 'github' as today).
3. For each stage with `artifact` set:
   - `git checkout -B <branch> <baseBranch>` (idempotent — create branch if not exists, switch if exists).
   - `git add <artifact>`.
   - `git commit -m "sdlc(<stage>): <artifact> accepted for cycle <id>"` (skip if nothing to commit).
   - `git push origin <branch>` (with `--set-upstream` on first push).
4. If every stage is `accepted`: call `platform.openPR(base, head, title, body, reviewers)` to open the PR; persist `cycleEntry.platform` and `cycleEntry.pr` to `cycle.json`.
5. Dry-run mode (`--dry-run`): do everything except commit/push/PR open — print the intended git commands and platform call.

Data flow:
- Input: `cycle.json`, `.loshu-sdlc/CODEOWNERS`, env (`GHCR_TOKEN`/`GITLAB_TOKEN` + `LOSHU_REPO`).
- Output: branch created/updated, commits made, PR opened (all stages accepted), `cycle.json` updated.

Error handling:
- Not in a git repo → `console.error("git sync: not in a git working tree")`; exit 2.
- No platform token → `console.error("git sync: set GHCR_TOKEN / GITLAB_TOKEN")`; exit 2.
- Stage artifact file missing → skip that stage with `console.warn`.
- `git` or `gh`/`glab` non-zero exit → bubble stderr, exit 1.
- cycle.json write failure → bubble, exit 1 (do NOT roll back pushed commits; user must reconcile).

Tests (new, in `tests/commands/git.test.ts`):
- Sync dry-run: stage iteration produces expected "would commit" lines (existing assertions preserved).
- Sync real (mocked execa): happy path — branch created, commits made, PR opened, cycle.json updated.
- Sync real, not in git repo → exit 2 with error.
- Sync real, no token → exit 2 with error.
- Sync real, no CODEOWNERS → reviewers defaults to empty.
- Sync real, mixed accepted/draft stages → only accepted stages commit (per the existing "has unaccepted stages — commit only, no PR" branch).

### 2. `rules check` — 4 Real Rules (commands/rules.ts)

Current behavior: stub report saying "pass" without actual check.

Target behavior:
- `list`: unchanged (already real).
- `check <name>`: dispatch to the rule's real implementation; otherwise return "pass" stub (preserved for the 7 borrowed rules).

Four rules to implement:

| Rule | Real impl |
|---|---|
| `eslint` | Spawn `npx eslint <globs>` via `execa`; capture stdout/stderr; pass = exit 0; surface first 5 errors |
| `intent-md-schema` | Use `validateArtifact('intent', path)` from `lib/validate.ts`; pass = valid; first errors are the validation error messages |
| `spec-md-schema` | Same with 'spec' |
| `plan-md-schema` | Same with 'plan' |

The other 7 rules (`a11y-wcag`, `security-owasp`, `code-review`, `coverage-threshold`, `attribution-provenance`, `tdd`, `verification-before-completion`) stay in their current "borrowed skill" stub state per spec phasing (real impls require the underlying skill ecosystems, deferred to v0.8+).

Rule registry shape: keep the existing `RULES` array; add a `runner?: (path: string) => Promise<RuleResult>` field that is filled for the 4 real rules and absent for borrowed ones. The `check` subcommand reads `rule.runner`, calls it if present, falls back to stub otherwise.

Tests (extend `tests/commands/rules.test.ts`):
- `check eslint` with mock execa (exit 0 → pass; exit 1 with stderr → fail with stderr surfaced).
- `check intent-md-schema` against real frontmatter (valid → pass; invalid → fail).
- `check <unknown>` → exit 2 with "unknown rule" message.
- `list` JSON output unchanged.
- Borrowed rule (e.g. `tdd`) → still returns the stub pass (proves the fallback path).

### 4. `upgrade` — Default Version Fix (commands/upgrade.ts)

- Add tests (currently zero).

### 5. v0.6.x Carryover (3 Minor Items from v0.6.4 Final Review)

#### 5.1 Export `STAGE_TO_SCHEMA` + fix `a.stage` registry lookup

New file `packages/cli/src/lib/stage-schema.ts`:
```ts
import type { Stage } from './identity.js';
export const STAGE_TO_SCHEMA: Record<Stage, string> = {
  plan: 'intent',
  design: 'spec',
  build: 'plan',
  test: 'claude-md',
  deploy: 'review',
  maintain: 'bands',
};
```

Modify `state.ts` to import from the new module (delete the local copy). Modify `versioning.ts` V2/V3/V4 to call `getArtifactTypeRegistry(reg, STAGE_TO_SCHEMA[a.stage])` instead of `getArtifactTypeRegistry(reg, a.stage)`. Fixes the latent bug.

Tests: existing V2 + V4 tests now exercise the corrected lookup; verify behavior unchanged for `plan`/`build` (where stage name == schema name) and corrected for the 4 stages that previously threw.

#### 5.2 `merged` consistency

The v0.6.4 TRANSITIONS table added `accepted → merged` and `merged → archived` per spec §3.1+§3.6, but `StageState` (cycle.ts:48-55) excludes `'merged'` per v0.6.3's reasoning (`'merged'` is a `PRRef['state']`, not a stage state).

Decision: remove the two `merged` rows from TRANSITIONS. The runtime type system rejects `state: 'merged'`, so allowing it as a transition target is a type-time lie. A user who wants to mark a cycle as merged sets `cycleEntry.pr.state = 'merged'` (via the platform adapter), not `cycleEntry.stages[X].state = 'merged'`. The spec diagram's `accepted → merged` is at the PR level, not the stage level — it manifests in `cycleEntry.pr.state`, not in `stage.state`.

If the spec really requires `merged` as a `StageState` value, that's a separate spec amendment (deferred). For v0.7.0 we resolve the inconsistency in favor of the type system.

Tests: verify TRANSITIONS table no longer contains `merged` as a key or value; existing C1 DAG tests still pass.

#### 5.3 `readFrontmatter` dedupe

Extract the three copies in `identity.ts:9-20`, `state.ts:49-54`, `versioning.ts:12-17` into `packages/cli/src/lib/accept/frontmatter.ts`. Each call site imports the shared helper. Variants:
- `identity.ts` and `versioning.ts`: take `path: string` → returns `Record<string, unknown> | null` (graceful on error).
- `state.ts`: takes `path: string` → returns `Record<string, unknown>` (empty {} on error).

Make two variants in the shared module: `readFrontmatterFile(path): Promise<Record<string, unknown> | null>` and `readFrontmatterFileOrEmpty(path): Promise<Record<string, unknown>>`. Each call site picks the variant matching its previous semantics.

Tests: existing tests should pass unchanged; add one new test for the shared helper.

## Data Flow

All four commands read from `.loshu-sdlc/state/cycle.json` (where applicable). `git sync` writes to cycle.json (mutates `cycleEntry.platform` and `cycleEntry.pr`). No new persistent state introduced.

`rules check` is read-only against the file tree + schemas.

`logs` reads `~/.loshu-sdlc/logs/*.log` (created by hooks; not modified by logs command).

`upgrade` reads + writes target project's `package.json`.

## Error Handling

- All commands return a non-zero exit code on failure; bubble error messages via `console.error`.
- `git sync` — never roll back partial work (push, commit, PR open). User must reconcile.
- `rules check` — fail-fast on rule runner error; preserve the stub path for borrowed rules.
- `logs` — empty log dir is not an error (returns `(no log entries)`); read errors per-file are caught individually.
- `upgrade` — missing package.json → exit 2; write errors → bubble.

## Testing Strategy

- Per-task TDD where it makes sense (rules check, upgrade, carryover).
- For git sync (the biggest piece): write tests against `execa` mock (same pattern as `tests/lib/platforms/github.test.ts`) — assert the right `git` and `gh` calls happen for each scenario. A real integration test (against a real git repo + GH token) is out of scope; the mock-level tests give us regression protection without requiring CI infrastructure.
- For logs + upgrade: real filesystem tests with mkdtemp.
- Test count goal: 201 → ≥215 (≈14 new tests).

## Risk Assessment

- **git sync (highest risk):** real `git`/`gh` invocation can corrupt working state if mishandled. Mitigations:
  - **`--dry-run` is the v0.7.0 default.** Real execution requires the explicit `--execute` flag. This makes day-to-day commands safe to run; real work is opt-in.
  - Strict preflight checks (in git repo? token set? cycle.json readable?) so day-to-day use fails fast without partial work.
  - Mock-level unit tests give us regression coverage.
  - Post-release decision: if the user wants the default flipped (dry-run off, execute on), that's a separate user-scoped change to v0.7.x — out of scope for v0.7.0.
- **rules check runner:** shelling out to `npx eslint` adds process spawn complexity. Use the existing `execa` pattern.
- **upgrade default-version:** must use `import.meta.url` resolution correctly for both published and monorepo layouts.
