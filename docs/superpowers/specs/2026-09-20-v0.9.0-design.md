# v0.9.0 Design — Maintain Loop Closure (auto-diagnose)

> **Status:** Draft (awaiting user review)
> **Date:** 2026-09-20
> **Target version:** v0.9.0

## Goal

Close the partial Maintain → Plan loop flagged in `docs/internal/playbook-coverage-analysis.md` (commit `28ea70e`) and dispositioned in `docs/superpowers/specs/2026-09-18-v0.8.0-backlog.md` §6.1.2 row "Auto-revert on failed merge" (deferred to v0.8.x as part of Maintain closure spec).

Currently: `maintain-exit.sh` detects 3σ breach, forks incident cycle in `cycle.json`, and **blocks** the gate until the user manually runs `/sdlc-maintain` to write a new `intent.md`. The "diagnose-and-write-back" half of the loop is currently user-driven.

After v0.9.0: `maintain-exit.sh` runs an agent-driven diagnose step when 3σ is breached, generates the incident `intent.md` content automatically (in the standard 4-field schema), writes it, persists the cycle + PR metadata, then continues the existing fork flow. The `/sdlc-maintain` slash command still exists for manual override.

## Non-Goals

- ❌ Background agent daemon (option B from brainstorming) — out of scope per user decision "A: hook 足够". The hook fires on `git sync` / push / manual run; no scheduler.
- ❌ Slack / webhook alerts (option C) — out of scope; deferred indefinitely.
- ❌ Auto-revert on failed merge — dispositioned to v0.9.x via the backlog, but its concrete spec arrives in a separate plan once Maintain loop is closed. (Maintain closure is a prerequisite for auto-revert.)
- ❌ New metrics types — `bands record` schema is unchanged.
- ❌ New acceptance assertions — C5-C8 dispositioned to v0.8.x-or-drop in v0.8.0 backlog.

## Architecture

One new helper command `loshu-sdlc maintain diagnose` that takes a bands.yaml breach report and writes an incident `intent.md` file. `maintain-exit.sh` invokes this helper automatically when the breach is detected, before the existing fork-and-block logic. The helper is also exposed for manual use (the existing `/sdlc-maintain` slash command can wrap it).

**No new daemon. No new persistent state beyond the existing incident `intent.md` and `cycle.json` fields.** The diagnose step runs inline at the hook, blocking the maintain-exit gate for ≤ 10 seconds (LLM call budget) before either succeeding (writes `intent.md` + proceeds to fork) or failing (falls back to today's "block and ask the user to run /sdlc-maintain" behavior — same UX as today if the LLM call fails).

## Components

### 1. `loshu-sdlc maintain diagnose` — new CLI subcommand

**Files:**
- Create: `packages/cli/src/commands/maintain.ts` (new file; or extend `packages/cli/src/commands/diagnose.ts` if preferred — pick whichever doesn't collide with existing names; `git.ts` is unrelated)
- Modify: `packages/cli/src/bin/loshu-sdlc.ts` (plumb the new subcommand)

**Interfaces:**

```ts
// packages/cli/src/commands/maintain.ts
export interface MaintainDiagnoseArgs {
  bandsPath: string;       // required: path to bands.yaml with breach
  metricsPath?: string;    // optional: path to .sdlc/metrics.json sidecar
  outputPath: string;      // required: where to write intent.md
  rootPath?: string;       // optional: defaults to dirname(bandsPath)
  // Future: --model, --dry-run (out of scope for v0.9.0)
}

export interface MaintainDiagnoseResult {
  status: 'written' | 'failed';
  intentPath: string;
  error?: string;
  durationMs: number;
}

export async function maintainDiagnose(args: MaintainDiagnoseArgs): Promise<MaintainDiagnoseResult>;
```

**Behavior contract:**

1. Read `bands.yaml` (frontmatter + body).
2. Read `.sdlc/metrics.json` sidecar if provided.
3. Construct a prompt asking the LLM (via whatever mechanism the CLI uses for LLM calls today — to be discovered; if no LLM client exists yet, see §1.1 below) to produce an `intent.md` for the breach. The prompt includes:
   - The cycle's current `cycle.json` state (which cycle, what stage each is in).
   - The bands.yaml definition of the breached metric (baseline, sigmas, evaluation rules).
   - The current observation value (from metrics.json) and the breach magnitude (e.g., "0.045 vs baseline 0.01, 4.5σ").
   - A short, opinionated prompt asking for: (a) problem statement, (b) proposed outcome, (c) affected components, (d) open questions.
4. Validate the LLM's output against `intent.schema.json` (existing `validateArtifact('intent', ...)`). If invalid, retry up to 2 times with corrections; if still invalid, return `status: 'failed'` with the validation errors so the hook falls back to today's behavior.
5. Write the validated `intent.md` to `outputPath`.
6. Return `MaintainDiagnoseResult`.

**§1.1 LLM client:** This plan does NOT add an LLM client. Instead, `maintainDiagnose` invokes `loshu-sdlc bands diagnose` — a new thin subcommand that simply **reads the breach data from bands.yaml and returns a structured JSON "diagnosis proposal"** (`{ problem, proposedOutcome, affectedComponents, openQuestions, suggestedIntentId }`). The CLI does NOT synthesize the `intent.md` itself; the agent invoking it (via Claude Code's slash command, OR via a future LLM client wired through `claude-cli` or similar) produces the natural language fields.

This keeps v0.9.0 **bounded**: no new external dependencies, no LLM API key management, no prompt injection surface in shipped code. The hook still works — it just produces a **stub `intent.md`** with structured fields from `bands diagnose`, and the agent (human or LLM) is responsible for filling in the natural-language fields before committing.

> **Implementation note (post-v0.9.0):** If `loshu-sdlc` already has an LLM client (e.g., from a prior PR I'm not aware of), replace the stub-with-diagnosis step with a real synthesis call. The spec is structured so the LLM integration is a single-file swap inside `maintainDiagnose`.

### 2. `packages/plugin/hooks/maintain-exit.sh` — diagnose before blocking

**Files:**
- Modify: `packages/plugin/hooks/maintain-exit.sh`

**Behavior change:** After 3σ detection (existing logic, ~line 122 onwards), before the "no incident intent found → block" branch, call `node "$CLI_BIN" maintain diagnose --bands "$BANDS" --output "$LATEST_INTENT"` with a 10-second timeout. If it succeeds, skip the block (the new intent.md satisfies the gate). If it fails or times out, fall back to today's "block and tell user to run /sdlc-maintain" behavior.

The 10-second timeout is enforced via a wrapper script (`timeout 10 node ...` on POSIX, equivalent on Windows) — explicit, not a hard-coded sleep.

### 3. `loshu-sdlc bands diagnose` — new thin subcommand

**Files:**
- Create: `packages/cli/src/commands/bands-diagnose.ts` (or add a `diagnose` sub-mode to `commands/bands.ts`)

**Behavior:**

1. Read `bands.yaml` + `.sdlc/metrics.json`.
2. For each metric currently in breach (above sigma_3), produce a structured JSON entry:
   ```json
   {
     "metric": "error_rate",
     "baseline": 0.01,
     "sigma_1": 0.015,
     "sigma_2": 0.02,
     "sigma_3": 0.03,
     "current": 0.045,
     "sigmaMagnitude": 4.5,
     "evaluation": "auto-3sigma",
     "evaluationTimestamp": "2026-09-20T10:00:00Z"
   }
   ```
3. Wrap in `MaintainDiagnosisProposal`:
   ```json
   {
     "breachedMetrics": [ ... ],
     "evaluationContext": {
       "cycleId": 2,
       "cycleTitle": "incident: error_rate (2026-09-20T10:00:00Z)",
       "previousCycleTitle": "..."
     },
     "suggestedIntentId": "plan-c02-..."  // from lib/identity.js generateId
   }
   ```
4. Write to stdout (caller is responsible for piping to `intent.md` or other sink).

**No LLM call.** This is pure mechanical extraction.

## Data Flow

```
git push / manual / scheduled CI
        ↓
maintain-exit.sh runs (existing)
        ↓
read bands.yaml + .sdlc/metrics.json
        ↓
loshu-sdlc bands evaluate (existing)
        ↓
3σ breach detected?
        ↓ yes
timeout 10 node loshu-sdlc maintain diagnose \
    --bands bands.yaml --output intent.md
        ↓
    inside maintainDiagnose:
    loshu-sdlc bands diagnose (extracts structured JSON)
    + (future) LLM call (stub for v0.9.0)
    + schema validate via validateArtifact
    + write intent.md
        ↓
diagnose succeeded?
        ↓ yes
    fork incident cycle + emit incident event (existing)
    exit 0  ← CHANGED: no longer blocks
        ↓ no (failure or timeout)
    fallback: block + tell user to run /sdlc-maintain (existing)
    exit 2
```

No new persistent state. The `intent.md` is the same artifact the user would have written manually; `cycle.json` is mutated the same way; `events.jsonl` gets the same entries.

## Error Handling

- **`maintainDiagnose` fails (LLM call error / schema validation fail):** return `status: 'failed'` with error details; the hook falls back to today's block-and-tell-user behavior. No silent data loss.
- **`maintain diagnose` exceeds 10 seconds:** `timeout` SIGTERMs the process; the hook catches non-zero exit and falls back the same way.
- **`bands.yaml` or `.sdlc/metrics.json` missing:** `bands evaluate` already handles this (returns empty incidents); the diagnose step is not reached. No new failure mode.
- **`intent.md` write fails (permissions / disk full):** `maintainDiagnose` returns `status: 'failed'` with the OS error; hook falls back.
- **LLM client unavailable (no API key, no `claude-cli`, etc.):** the stub-with-diagnosis path works without LLM — produces an `intent.md` with structured fields from `bands diagnose`, leaves the natural-language fields as TODO. The hook still exits 0; the agent (human or LLM) fills in the natural-language fields before committing. This is the **degraded-mode contract**: maintain loop still closes, but the quality of the incident intent is lower than a full LLM synthesis would produce.

## Testing Strategy

- **Unit tests** for `loshu-sdlc bands diagnose` (pure extraction — easy to test):
  - Single-metric breach → emits one entry with correct sigma-magnitude.
  - No breach → emits empty `breachedMetrics`.
  - Malformed bands.yaml → returns error.
- **Unit tests** for `loshu-sdlc maintain diagnose`:
  - Mock the LLM client (future) or assert the stub output for now.
  - Schema-validate the output intent.md → reject on validation failure, retry, then fail.
- **Shell tests** for `maintain-exit.sh`:
  - Existing behavior preserved when `bands diagnose` is absent or fails (the fallback path).
  - New behavior: when diagnose succeeds, hook exits 0 (no block) and intent.md is written.
- **Integration test**: the existing `closed-loop.test.ts` extended to assert that with `maintain diagnose` available, the loop closes without manual intervention.

## Risk Assessment

**Medium risk** — this is the first release that touches `maintain-exit.sh` since v0.6.4. The existing behavior must be preserved exactly when the diagnose step fails or is absent. Mitigations:
- **Degraded-mode contract** is explicit: the diagnose step is OPT-IN (only runs when `loshu-sdlc maintain diagnose` exists and returns success); failure falls back to today's behavior. The hook is **never worse than today**.
- The 10-second timeout prevents the diagnose step from blocking the gate indefinitely if the LLM call hangs.
- The stub-with-diagnosis path (no LLM call) means the feature works even in environments without an LLM API key — degraded quality, but the loop still closes.
- Tests cover both branches (success and failure fallback).

**Specific risks:**
- The new shell code in `maintain-exit.sh` could break the existing 3σ fork flow. Mitigation: shell test that exercises the success path AND the existing-only path (no diagnose binary available).
- The `loshu-sdlc maintain diagnose` binary might not be in PATH for the hook. Mitigation: the hook uses the existing `node "$CLI_BIN"` pattern (line ~138 in current maintain-exit.sh), so it relies on the same CLI_BIN resolution that the existing `bands evaluate` call uses.
