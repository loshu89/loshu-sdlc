# v0.1.1 Phase 4 Report — Release Infrastructure

## Summary

Added release infrastructure for v0.1.1: a tag-triggered GitHub Actions workflow that publishes to npm and creates a GitHub Release, a local release helper script, the v0.1.1 changeset entry, marketplace-friendly metadata in `plugin.json`, and a refreshed `README.md` that documents the v0.1.1 feature set.

## Files Created

### 1. `.github/workflows/release.yml`

GitHub Actions workflow triggered by `push: tags: ['v*']`.

- Runs the full CI gauntlet: `pnpm install --frozen-lockfile` → `typecheck` → `test` → `build` → `lint` → `test:eval:strict`.
- Then runs `changesets/action@v1` with `publish: pnpm changeset publish` to bump, publish, and emit a GitHub Release.
- `permissions: { contents: write, pull-requests: write }` lets `changesets/action` create the release.
- `NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}` is required for the npm publish step (set this secret on the repo before tagging).

Validation: parsed cleanly with `js-yaml`; the resulting object has `name=release`, `on.push.tags=[v*]`, the expected 10 steps, and the correct env block.

### 2. `scripts/release.mjs`

Local release helper. Usage: `node scripts/release.mjs <version>`.

Sequence:
1. Validates `<version>` is semver (`x.y.z` or `x.y.z-tag`).
2. `checkCleanTree()` — `git status --porcelain` must be empty.
3. `runCiGauntlet()` — runs `pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm lint`, `pnpm test:eval:strict`. Aborts on any non-zero exit.
4. `bumpPackages(version)` — writes the new version into all three workspace `package.json` files (`@loshu-sdlc/plugin`, `@loshu-sdlc/cli`, `@loshu-sdlc/templates`).
5. `refreshLockfile()` — `pnpm install --lockfile-only` so the lockfile tracks the new pins.
6. `commitRelease(version)` — `git add -A && git commit -m "chore: release v<version>"`.

The script does **not** push, tag, or publish. Tag + push happens manually after the commit, and the GitHub Actions workflow takes over from there. The script ends by printing:

```
git tag v<version>
git push origin main v<version>
```

Validation:
- `node --check scripts/release.mjs` — syntax OK.
- `node scripts/release.mjs` (no args) — aborts with "missing version argument".
- `node scripts/release.mjs not-semver` — aborts with "is not a valid semver".
- The `bumpPackages` logic was exercised end-to-end with an isolated `0.1.1-test` version against the three real `package.json` files; all three were bumped and then restored to `0.1.0`.

## Concerns

1. **Pre-existing lint failures block the CI gauntlet.** `pnpm lint` fails with 18 errors on `main` before any of my Phase 4 changes are applied. The errors live in `packages/cli/src/...` and `tests/evals/run.ts`. Because `release.mjs` runs the full gauntlet (`pnpm lint` included), invoking it on the current `main` will correctly abort at the lint step. The script itself is fine — it's doing what it should. The lint errors are a separate pre-existing defect from earlier phases that should be triaged before the actual v0.1.1 tag is cut.
2. **`scripts/release.mjs` is linted-out by `.eslintrc.json`'s `ignorePatterns: ["*.mjs"]`.** This is intentional and matches the existing `scripts/copy-plugin.mjs` convention (also a `.mjs` script). The script still gets `node --check` syntax validation and is exercised end-to-end via the isolated bump test.
3. **`npm publish` requires `NPM_TOKEN` to be set on the GitHub repo.** The release workflow uses `${{ secrets.NPM_TOKEN }}`. If this secret is missing, the `changesets/action` publish step will fail with an auth error. This is a one-time repo-secret setup, not a code issue.
4. **Marketplace installation commands are illustrative.** The README quickstart uses `claude plugin marketplace add ...` and `claude plugin install ...` syntax. Exact CLI subcommand names depend on the Claude Code marketplace spec; the README may need a tweak once the plugin is actually published and the marketplace UX is exercised end-to-end.
5. **`tests/evals/results.json` is a regenerated artifact.** Every `pnpm test:eval:strict` invocation rewrites it with a new `generatedAt` timestamp and the new mode (`strict` vs `loose`). It is currently committed (presumably as a stable baseline) and was not touched by my Phase 4 changes. I reverted a small diff the verification run produced so my Phase 4 commit is noise-free.
