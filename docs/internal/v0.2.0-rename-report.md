## Concerns

### CRITICAL — scope-vs-owner mismatch will break GitHub Packages publishing

**GitHub Packages' npm registry requires `scope = GitHub owner/org`.**
The repo is now owned by **`loshu89`** (a user), but the npm scope is
**`@loshu-sdlc`**. The original v0.1.1 rename to `@maxsun1989/*` was done
*specifically* to make `scope = owner`. We have undone that rename, which
will re-trigger the same E401 authentication error we just hit.

The publish workflow (`.github/workflows/publish-ghcr.yml`) will fail with
the same error until one of the following is true:

1. **Transfer the repo to a `loshu-sdlc` GitHub org.** Then
   `@loshu-sdlc/*` packages publish cleanly. (This was explicitly rejected
   during v0.1.1 planning in `docs/v0.1.1-ghcr-publish-migration-report.md`.)

2. **Rename the user account** from `loshu89` to `loshu-sdlc`. GitHub does
   not allow renaming personal accounts, so this is effectively impossible.

3. **Publish under a different registry** (npmjs.org public registry) and
   drop GitHub Packages. Then scope = owner is irrelevant.

4. **Keep `@maxsun1989/*` scope** and rename *the GitHub owner* of the
   repo back to `maxsun1989`, or transfer the repo to a user/org whose
   login matches the scope.

The user must decide which path to take before the next release. This
rename commit is reversible (one revert) but the lockfile and
`pnpm-lock.yaml` will need regeneration again.

### Other concerns

- **No version bump applied yet.** The v0.2.0 changeset is a "pending
  change" in the changesets system. To turn it into a release, run
  `pnpm version` (which invokes `changeset version`) followed by
  `scripts/release.mjs v0.2.0`. Until then, the workspace packages still
  carry their v0.1.x versions in `package.json`.

- **Bundled plugin copy is now stale.** `packages/cli/plugin/` is a
  checked-in copy of `packages/plugin/`. It was regenerated by
  `pnpm build` during verification, but the regenerated files are not
  tracked as their own diff because they're identical to the source after
  our rename edits. If `pnpm build` were run against the unrenamed source,
  the bundled copy would diverge. This is the same situation as before
  the rename — see `scripts/copy-plugin.mjs` comments.

- **`.changeset/v0.1.1.md` kept with renamed package entries.** This was
  the "update package names (or delete)" option from the brief. We chose
  rename to preserve the historical record of the v0.1.1 release. If the
  changesets version step references these entries, it may complain.
  Safer option would have been to delete it.

- **The `homepage` field in `plugin.json` points at the new owner.** The
  Claude Code marketplace uses this as the plugin homepage; it should
  work as long as the repo remains public.

- **`pnpm-lock.yaml` was regenerated**, but no new transitive deps were
  pulled in. Verified by re-running `pnpm install` twice and confirming
  the lockfile is stable.
