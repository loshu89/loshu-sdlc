# v0.1.1 → GitHub Packages Migration Report

**Date:** 2026-09-14
**Goal:** Rename `@loshu-sdlc/*` npm packages to `@maxsun1989/*` so the repo owner (`maxsun1989`) matches the npm scope required by GitHub Packages; add a GitHub Packages publish workflow.

## Why

GitHub Packages' npm registry requires `scope = GitHub owner/org`. The repo lives under the `maxsun1989` GitHub owner. Renaming the scope (instead of creating a separate `loshu-sdlc` GitHub org) keeps the publish path frictionless.

The Claude Code marketplace identifier `loshu-sdlc@loshu-sdlc` (plugin name from `plugin.json`) is unchanged — only the **npm scope** is renamed.

## Section 4 — Publish workflow (commit 2)

`D:/workspace/3.my/SDLC/.github/workflows/publish-ghcr.yml`:

- **Triggers:** push of `v*` tag, manual `workflow_dispatch`
- **Permissions:** `contents: read`, `packages: write` (gives `GITHUB_TOKEN` the ability to publish)
- **Steps:**
  1. Checkout (depth 0 for changesets)
  2. pnpm@9, Node 20 (registry = `https://npm.pkg.github.com`)
  3. `pnpm install --frozen-lockfile`
  4. `pnpm typecheck`
  5. `pnpm test`
  6. `pnpm build`
  7. `pnpm test:eval`
  8. `pnpm config set //npm.pkg.github.com/:_authToken $GITHUB_TOKEN`
  9. `pnpm -r --filter './packages/*' publish --access public --no-git-checks --tag latest`

This is independent of `.github/workflows/release.yml` (which uses `changesets/action` and the public npm registry). The user opted into GitHub Packages — `release.yml` is left untouched for now; if the user wants GitHub Packages to be the canonical release path, `release.yml` should be deprecated or merged into `publish-ghcr.yml` in a follow-up.

## Concerns

1. **`.github/workflows/release.yml` (existing) still publishes to the public npm registry** (`registry.npmjs.org`) via `changesets/action`. This is **stale** — the npm packages no longer exist at `@loshu-sdlc/*` on npm; a `release.yml` run on the next tag would fail (npm 404). The new `publish-ghcr.yml` is the canonical publish path going forward. **Recommendation:** in a follow-up commit, either delete `release.yml` or update it to use the same publish-ghcr workflow. Left in place here to keep this change minimal and reviewable.

2. **`pnpm publish --filter './packages/*'` does not honor workspace ordering.** The three packages (`plugin`, `cli`, `templates`) have no inter-publish dependency, so this works. If a future package depended on another at publish time (e.g., `cli` depended on a `@maxsun1989/plugin` version in its published `dist/`), we'd need a topological sort. Not an issue today.

3. **`registry-url: https://npm.pkg.github.com` in `setup-node` makes the *install* step use GitHub Packages too.** This works because the package names match the GitHub owner, but if any transitive dep lived under a different GitHub owner it would fail with 401/404. Today, all non-`@maxsun1989/*` deps are public npm packages and won't be affected. If install failures appear during the first publish run, swap to using `registry-url` only for the publish step.

4. **`.npmrc` env-var warning in local dev** (`Failed to replace env in config: ${NPM_TOKEN}`) is cosmetic; only the publish step needs the token. Local `pnpm install` works fine because all dependencies are public npm packages.

5. **`--no-git-checks`** in the publish step bypasses pnpm's dirty-tree and version-already-published checks. This is intentional for CI (the workflow guarantees a clean checkout via `actions/checkout@v4` on a tag), but it means a re-run on the same tag will not error. If re-runnability becomes important, drop this flag.

6. **Historical phase reports (`v0.1.1-phase-2-report.md`, `v0.1.1-phase-4-report.md`) still describe the old `@loshu-sdlc/*` package names.** These are intentionally frozen as v0.1.1-shipped artifacts; they describe what shipped, not current state. Out-of-scope for this rename.

7. **Bundled plugin copy** (`packages/cli/plugin/`) is gitignored and rebuilt by `scripts/copy-plugin.mjs` on every `pnpm build`. The committed source-of-truth is `packages/plugin/`; the bundled copy is derived. Verified after build that the new package name and metadata propagate correctly.
